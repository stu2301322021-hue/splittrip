# ST-12 — Спецификация на изчисляване и записване на дяловете

Parent: ST-8
Резултат: спецификация; алгоритъмът и атомарният запис
не са реализирани.

## Вход и изход

Вход:
- ID на пътуване и платец;
- описание, валидирано според ST-11;
- положителна сума C в цели евроцентове;
- непразен списък от уникални ID на участници.

Платецът и всички участници трябва да принадлежат
на избраното пътуване.

Изход при успех:
- ID на записания разход;
- списък от участници и техните дялове в евроцентове.

## Алгоритъм

1. Подреждаме ID на участниците във възходящ ред.
2. N е броят на участниците.
3. Изчисляваме основен дял: C // N.
4. Изчисляваме остатък: C % N.
5. На първите „остатък“ участници добавяме по 1 евроцент.

Псевдокод:

    ids = sort(participant_ids)
    base = C // len(ids)
    remainder = C % len(ids)

    for index, participant_id in enumerate(ids):
        share = base + (1 if index < remainder else 0)
        result.append((participant_id, share))

Невалидният вход се отхвърля преди изпълнение.
Повторени ID не се премахват мълчаливо.

## Примери

| Сума в центове | Входни ID | Получени дялове по ID |
| --- | --- | --- |
| 6000 | 2, 5, 8 | 2:2000, 5:2000, 8:2000 |
| 1000 | 8, 2, 5 | 2:334, 5:333, 8:333 |
| 1001 | 2, 5, 8 | 2:334, 5:334, 8:333 |
| 1 | 2, 5 | 2:1, 5:0 |
| 999 | 5 | 5:999 |

## Гаранции на алгоритъма

- Сборът на дяловете е точно C.
- Всички дялове са неотрицателни цели числа.
- Разликата между най-големия и най-малкия дял е най-много 1 цент.
- Редът на входните ID не променя резултата.
- Всеки избран участник получава точно един дял.

## Атомарен запис

1. Започва една транзакция.
2. Проверява се наличието на пътуването и принадлежността
   на платеца и получателите в рамките на транзакцията.
3. Изчисляват се дяловете.
4. Добавя се един запис в expenses.
5. Получава се ID на новия разход.
6. Добавят се всички дялове в expense_shares с това expense_id.
7. Транзакцията се потвърждава с COMMIT.
8. Едва след успешен COMMIT се връща потвърждение.

При грешка се изпълнява ROLLBACK.
Не остава нито новият разход, нито част от неговите дялове.
Предишните разходи не се променят.

Заявките използват параметри за входните стойности.
Записът на всеки отделен дял не прави собствен COMMIT.

## Проверки при бъдещата реализация

- Всеки пример от таблицата дава точния очакван резултат.
- Празен списък, повторени ID или неположителна сума се отхвърлят.
- Несъществуващ или чужд участник не води до нов разход.
- Принудителна грешка при втория дял отменя и първия,
  и самия разход.
- След успешен запис и повторно отваряне на базата
  разходът и всички дялове са налични.

Това са планирани проверки, а не изпълнени тестове.
